# Нотатки для розробників

Як [`bf2font.py`](../bf2font.py) перетворює `.mcm` від Betaflight на PNG та
файли шрифтів, і як запустити його на своїх шрифтах.

## Запуск

Залежності керуються через [uv](https://docs.astral.sh/uv/). Скрипт ще й має
вбудовані метадані PEP 723, тому запускається окремо звідки завгодно.

```bash
uv run bf2font.py original_fonts/default.mcm
```

```bash
uv run bf2font.py original_fonts/*.mcm -o output --scale 16
```

| Опція | Що робить |
| --- | --- |
| `-o, --output` | тека виводу (типово `output`) |
| `-s, --scale` | масштаб PNG; 1 піксель OSD = N пікселів зображення (типово `8`, тобто 96×144 на символ) |
| `--formats` | будь-яка підмножина з `otf,ttf,woff,woff2` |
| `--family` | точна назва гарнітури, лише для одного вхідного файлу |
| `--family-prefix` | префікс для назви (типово `Betaflight OSD`) |
| `--literal-ascii` | лишити `a-z` на їхніх слотах із символами, не зводити на великі літери |
| `--no-ascii-cmap` | мапити символи лише за `U+E000 + індекс` |
| `--no-layer-fonts` | не робити пласкі гарнітури `Shadow` і `Fill` |

Вивід на кожен вхідний файл:

```
output/<name>/
├── png/000.png … 255.png    по одному PNG на символ, прозорий фон
├── <name>_sheet.png         атлас 16×16 з усім набором
├── <name>.json              індекс → шлях до PNG, кодпойнт, ASCII, ознака пустого
└── fonts/
    ├── otf/                 <Family>.otf, <Family>Shadow.otf, <Family>Fill.otf
    ├── ttf/                 ті самі три гарнітури
    ├── woff/
    └── woff2/
```

## Формат `.mcm`

Це дамп пам'яті символів MAX7456: рядок `MAX7456`, далі 16384 рядки по вісім
двійкових цифр, тобто 256 символів × 64 байти. Перші 54 байти символу це 12×18
пікселів по два біти, рядок за рядком. Решта 10 байтів це заповнювач (`0x55`).

| Значення | Піксель |
| --- | --- |
| `0b00` | чорний |
| `0b10` | білий |
| `0b01`, `0b11` | прозорий |

Саме через це кодування символ Betaflight білий із чорною обводкою, і саме
тому одноколірний шрифт не може передати його чесно.

## Пікселі → контури

З кожного символу виходить два набори пікселів: **силует** (чорні + білі) і
самі **білі** пікселі.

Обидва векторизуються трасуванням межі. Кожна клітинка додає ті одиничні
ребра, з іншого боку яких клітинки немає, орієнтовані так, щоб залита область
була ліворуч. Зчеплення таких ребер дає зовнішні контури проти годинникової
стрілки, а дірки за годинниковою, що правильно для правила ненульового
заповнення. Там, де дві клітинки дотикаються лише кутом, з однієї вершини
виходить кілька ребер, тож обхід бере найкрутіший поворот праворуч і контури не
перетинаються. Точки на одній прямій потім прибираються.

У TrueType напрямок контурів протилежний до PostScript, тому для `glyf`
контури розвертаються.

## Кольорові гліфи

Колір дають `COLR` v0 / `CPAL` з палітрою на два записи: чорний і білий.
Кожен символ це три гліфи:

| Гліф | Що в ньому |
| --- | --- |
| `bfXX` | силует, базовий гліф; його малюють ті, хто не знає `COLR` |
| `bfXX.black` | силует, колір з індексу 0 |
| `bfXX.white` | лише білі пікселі, індекс 1, малюється зверху |

Білий шар лежить поверх **повного** чорного силуету, а не поруч із самими лише
чорними формами. Дві заливки різного кольору встик лишають волосяні щілини від
згладжування на шві; з перекриттям такого немає.

Програми, які не читають `COLR`, малюють базовий гліф, тому Figma й показує
пласкі одноколірні літери. Для них `--layer-fonts` увімкнений типово, і кожен
шрифт виходить ще у двох пласких гарнітурах: у `Shadow` кожен гліф це силует, у
`Fill` лише білі пікселі. Вони з тих самих контурів і метрик, що й кольоровий
шрифт, тож два накладені текстові шари дають точно його.

`COLR`/`CPAL` не залежать від формату контурів, тому однакова побудова йде і в
CFF `.otf`, і в `glyf` `.ttf`. Вебфайли це той самий TTF, загорнутий у WOFF і
WOFF2: у контурів `glyf` ширша підтримка кольорових шрифтів.

## Метрики

| | |
| --- | --- |
| Одиниць на em | 1800 (100 одиниць на піксель OSD) |
| Ширина символу | 1200 (12 пікселів), моноширинний |
| Верхній / нижній виносний | 1400 і -400, 18-піксельна клітинка вміщається між ними |

Ліві напівапрош (`lsb` у `hmtx`) беруться з реального `xMin` кожного гліфа.
TrueType позиціонує гліфи саме за `lsb`, тож глухий нуль зсуває кожен гліф убік.

## Мапа символів

- `U+E000 + індекс` дає всі 256 символів, завжди.
- `0x20-0x7E` додатково мапляться на свої ASCII-кодпойнти, плюс `U+00A0` на
  пустий символ.
- `a-z` зведені на великі літери, бо малих у Betaflight немає, а в тих слотах
  лежать стрілки й символи. `--literal-ascii` лишає їх на своїх місцях; у
  будь-якому разі ці символи доступні за своїми `U+E0xx`.

## Як перевірити зміни

Контури точно оборотні, тому круговий прогін це справжній тест: розтеризуй
протрасовані контури за правилом ненульового заповнення в центрах пікселів і
порівняй із вихідним растром. Обидва шари всіх 256 символів у десяти вкладених
шрифтах дають 5120 наборів контурів.

Рендер перевіряй окремо. `ImageFont` з Pillow і `embedded_color=True`
растеризує `COLR`/`CPAL` через FreeType і ловить помилки в шарах та палітрі,
яких порівняння контурів не побачить.
